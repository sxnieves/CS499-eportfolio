Professional Self-Assessment

Where I started, and where this program leaves me

Putting this ePortfolio together has been a good excuse to actually look back at everything I've built over the course of this program, instead of just moving on to the next assignment. I work full-time as a Microsoft Cloud Administrator and Director of Project Services, so most of my computer science education has happened in parallel with real IT work — troubleshooting Active Directory issues one night, then writing recursive algorithms for a data structures assignment the next. That back-and-forth has shaped how I think about software: less like an academic exercise and more like something that has to actually hold up when real people depend on it.

Collaborating in a Team Environment

Most of what I've learned about collaboration didn't come from a group project in this program — it came from my job. I support a healthcare organization's Microsoft 365 and Intune environment, which means I'm constantly coordinating with vendors, clinical staff, and other IT team members who don't share my technical background. Rolling out something like two-factor authentication to a staff base that's genuinely resistant to change taught me more about communication and buy-in than any solo coding assignment could. In the program itself, courses like CS 250 (Software Development Lifecycle) reinforced the same idea in a more structured way: code reviews, sprint planning, and documentation only work if the people around you can actually follow what you did and why.

Communicating with Stakeholders

Explaining technical work to a non-technical audience is something I do almost daily — drafting IT communications about domain trust errors, putting together procurement requests, or explaining to leadership why a legacy system needs to be replaced. That skill translated directly into this capstone. The code review video and the artifact narratives in this ePortfolio weren't written for another developer looking over my shoulder; they were written for an audience that includes managers, recruiters, and people evaluating whether I can explain my own work clearly.

Data Structures and Algorithms

My enhancement to the Travlr Getaways application is the clearest example of this outcome. The original project had a basic, unindexed search function. I added MongoDB text indexing on the backend and built a debounced search feature on the Angular frontend, so the application queries the database more efficiently and doesn't hammer the server with a request on every keystroke. It was a small-looking change with real trade-offs behind it — index size versus query speed, responsiveness versus server load.

Software Engineering and Database

The software design and database enhancements on the same Travlr application round this out. I built out full CRUD functionality, added validation, and hardened the security of the existing code, then followed that with database-layer improvements in Milestone Four. Working across the whole stack — from the Angular frontend down to the MongoDB collections — gave me a much better feel for how a design decision in one layer ripples into the others.

Security

Security isn't a bolt-on for me — it's baked into almost everything I touch professionally, from MFA and RBAC rollouts to reviewing legacy Group Policy objects for consolidation. That mindset showed up directly in the Travlr enhancements, where I hardened input validation and access control as part of the software design work, and it shaped how I approached the database enhancement too.

How the Artifacts Fit Together

All three enhancements in this ePortfolio build on a single artifact, the Travlr Getaways MEAN stack application, rather than three unrelated projects. I chose that route on purpose: it let me show growth across the full stack — frontend, algorithms, and database — on one coherent piece of software instead of a handful of disconnected demos.
